Field notes from five other languages

A survey of documented bugs, footguns, and compiler-optimizer miscompilations in C, C++, Go, Rust, and a filtered pass over C#, Java, Python, JavaScript, and PHP — read specifically against Postulate's own feature set, to seed the next round of black-box test cases for Edsger.

5 parallel research passes ~90 findings surveyed filtered for Postulate relevance 2026-08-31
Cross-cutting priorities C C++ Go Rust C#/Java/Py/JS/PHP

Where independent research converged

These items surfaced from more than one language track without prompting — the strongest signal in this whole survey that they're structural, not language trivia. Ranked as a rough "write this test first" order.

01

Fixed-width integer overflow has no decided policy yet

Wrap, trap, UB, or an explicit checked_*/wrapping_* API family — C leaves it UB and lets opt exploit that; Go and Rust each argue with themselves about it for a decade. Pick one per operation, per width, and write it down before it becomes accidental behavior.

CGoRustManaged
02

INT_MIN / -1 and -INT_MIN

Two's-complement's one true asymmetry: the positive range is one short. x86 idiv traps on it (SIGFPE-shaped), C calls it UB, Go has a four-year-old open issue about it. Needs a defined answer at every signed width — int8 through int64.

CGoManaged
03

Wrong nsw/nuw/noalias hints under opt

The single most directly actionable finding in the whole survey: LLVM's poison-generating and no-alias attributes are a contract the frontend makes with the optimizer. Get it wrong and the miscompilation is silent — documented, real, and recurring in both Rust's and LLVM's own history, on the exact pipeline Edsger now shares.

C++RustC
04

Pointer↔uintptr↔pointer round-trips under optimization

Provenance is a real, separate concept from the bit pattern in LLVM's model. A cast-away-and-back pointer can legally be treated as a "different" pointer by an aggressive alias analysis — exactly the reinterpret idiom Postulate's as-casts invite.

CRust
05

The NaN quirk is a real deviation, not a curiosity

Every mainstream language guarantees NaN != NaN is true — the one universally-relied-on NaN property. Postulate's ordered-fcmp lowering makes it read false instead. Confirmed independently by two research tracks as the highest-priority float finding.

ManagedGo
06

Struct-copy semantics at every access path

C#'s "mutate through a property getter, the write vanishes" and Go's "value-receiver mutates a copy" are the same bug: an access path that looks like an lvalue but silently hands back a temporary. Postulate structs are value types too — prove every access path (return value, field chain, array element) is unambiguous.

ManagedGo
07

Operator-overload consistency is unenforced

A confirmed, existing Postulate gap: nothing stops == being declared without a matching !=, or in only one operand order. C#'s GetHashCode mismatch class and C++'s member-vs-free-function asymmetry are the same root cause wearing different clothes.

C++Managed
08

Cross-file symbol mismatch should be a hard error

C/C++ linkers match symbols by name only, never by signature — the mechanical root of ODR violations, real ones, in Firefox and MySQL. Edsger's own multi-file use resolution can close this gap outright by re-checking every imported signature against its real definition, something C++ structurally never did.

C++
09

Uninitialized reads and LLVM's poison semantics

An undef/poison value can legally evaluate to a different concrete value each time it's read — a documented source of real LLVM miscompilations. Postulate's manual mmap/stack memory has no auto-zero anywhere; this is inherited by construction, not by choice.

C
10

No memory model for the raw futex/clone primitives

A compiler that assumes single-threaded execution can legally turn a busy-wait spin-loop on shared memory into an infinite loop with the check hoisted out. Go's own scheduler has shipped real lost-wakeup bugs on the exact futex pattern Postulate's future std::mutex will need to get right.

CGo
11

own *T/ghost-map vs. Rust's two failure histories

Rust's borrow checker has a well-documented false-positive history (self-reference, disjoint fields, flow-insensitivity) and, separately, a noalias-attribute miscompilation history. Postulate's ghost-map design sidesteps the first by construction — but inherits the second the moment it starts emitting alias hints from ownership info.

Rust
12

Generic diagnostics: design the constraint check before the constraint

C++ fails deep inside the generic body because there's no declared contract to check against until instantiation; Go's pre-1.18 debate and its awkward constraints.Ordered workaround for "no operator overloading" are the same problem from the other side. Postulate has real overloading already — generics should be designed to use it directly, not reinvent Go's interface plumbing.

C++Go

C

mandatory

C's own literature is almost entirely about one mechanism: the optimizer is licensed to assume undefined behavior never happens, and then reasons backward from that assumption to delete the code that would have handled it. Every entry below is a variation on that one theme — which makes it the most load-bearing research track for Edsger's brand-new opt pipeline specifically.

Signed overflow licenses loop/branch elimination

Because signed overflow is UB, for (i = 1; i > 0; i += i) can be optimized to an unconditional infinite loop — GCC has shipped exactly this at -O2/-O3 on real, innocent-looking code.

for (int i = 1; i > 0; i += i) { ... }
// -O2: becomes while(true) -- overflow "can't happen"
Test

Compile the same overflow-adjacent loop at every -O level and diff the runtime result, not just "does it compile."

Sources: Krister Walfridsson · CERT INT32-C

Null-check deleted because an earlier dereference "proved" non-null

CVE-2009-1897 (Linux tun driver): GCC saw tun->sk dereferenced, concluded tun can't be null, and deleted the if (!tun) guard written after it — a real privilege-escalation bug.

struct sock *sk = tun->sk;   // dereference
if (!tun) return -EBADFD;    // deleted: "tun is already proven non-null"
Test

Dereference-then-null-check on the same pointer, at -O2: the check must not silently disappear.

Source: Check Point Research, OptOut

A pointer past the array end is UB before it's even dereferenced

a + 11 on a 10-element array is UB the moment it's computed, whether or not it's ever read — and this licenses eliminating bounds-check idioms built on "the pointer will just be wrong, not undefined."

int a[10];
int *p = a + 11;  // UB at computation time, no read needed
int *q = a - 1;   // also UB
Verdict

Directly applicable — Postulate's pointer arithmetic (p+n, p1-p2) is a real, named language feature. Test transient out-of-bounds intermediates specifically.

Sources: Walfridsson, "C pointers are not hardware pointers" · CERT ARR30-C

Strict aliasing breaks type-punning through a cast

Writing through a float* obtained by casting an int* is UB under -fstrict-aliasing (on by default at -O2+); real projects (the Linux kernel among them) build with -fno-strict-aliasing specifically because this bites production code.

float f = 1.0f;
int *ip = (int*)&f;
*ip = 0;             // may not be observed through f at -O2
printf("%f\n", f);   // surprising result
Verdict

Postulate's pointer↔pointer reinterpret as-casts are exactly this idiom. Test a write-then-read round trip through a reinterpreted type at every -O level.

Sources: Red Hat Developer · Regehr

Struct padding leaks and defeats memcmp

Padding bytes between fields are unspecified content; comparing two field-identical structs byte-for-byte can report them unequal, and copying a struct wholesale can leak stale stack contents (CVE-2010-4083).

struct S { char a; int b; };  // padding after a
struct S x = {1,2}, y = {1,2};
memcmp(&x, &y, sizeof(S));    // not guaranteed equal
Verdict

Postulate structs use natural/ABI alignment — the same padding exists. Any future struct-equality operator must compare field-by-field, never byte-by-byte.

Dead-store elimination deletes security-motivated zeroing

A memset that zeroes a secret right before it goes out of scope is a classic optimizer target: if nothing reads the buffer afterward, the write is "dead" and gets removed — CWE-14, still a live footgun without memset_s or a volatile-shaped escape hatch.

Verdict

Postulate has no libc/allocator wrapper yet, but the same shape recurs the moment someone wants to scrub memory before sys_munmap. Worth a "don't optimize this write away" primitive before it's needed.

Source: OWASP: Insecure Compiler Optimization

The optimizer assumes single-threaded execution

A data race is UB in the C/C++ memory model, so a spin-loop reading shared memory with no explicit fence can be hoisted into an unconditional infinite loop — the compiler is allowed to assume the flag never changes "on its own."

while (ready == 0) { }  // may become an unconditional loop without a fence
Verdict

Postulate's threading is raw sys_clone/sys_futex with no declared memory model yet. A busy-wait on shared memory is exactly this pattern — needs an explicit answer before opt is trusted near it.

Source: Compiler Optimizations under a Race Condition

Poison/undef values can evaluate differently on each read

LLVM's undef semantics let a single "uninitialized" value resolve to different concrete values at each use — a real, documented source of miscompilation in LLVM's own history (the phi(X, undef) → X transform bug).

Verdict

Edsger emits LLVM IR directly and now runs it through opt — this is inherited, not chosen. Test a doubly-used uninitialized local at -O0 vs. -O2 for consistency.

Sources: LLVM UB manual · Lee et al., Taming Undefined Behavior in LLVM (PLDI'17)

restrict-shaped aliasing assumptions on ref parameters

C's restrict tells the optimizer two pointers never overlap; if the caller aliases them anyway, a vectorized/reordered loop body silently produces the wrong answer.

Verdict

If Edsger's backend ever auto-attaches noalias to ref parameters, aliased-ref arguments become exactly this bug. Test two ref parameters bound to the same variable.

Shift by ≥ the type's width

x << 32 on a 32-bit value is UB; most hardware masks the shift amount instead of shifting to zero, so the "obviously wrong" result (x unchanged) is what actually ships on many backends.

uint32_t x = 1;
uint32_t y = x << 32;  // UB; often y == 1 on real x86 codegen, not 0
Verdict

Test every fixed-width shift with an amount ≥ the type's own bit width — needs a defined, documented result, consistent across -O levels.

Source: CERT INT34-C

Reinterpreting raw bytes as bool risks a trap representation

A bool/_Bool that isn't bit-pattern 0 or 1 (via type-punning) is UB; a switch compiled to a jump table can then branch to an arbitrary address on the "impossible" value.

Verdict

Postulate allows exactly this kind of reinterpretation. Test a byte-reinterpreted bool that isn't strictly 0/1 flowing into a branch, at every optimization level.

Uninitialized reads as information leaks

Reading an uninitialized struct field in practice often returns a previous stack/heap occupant's data — the root of the Samba ACL-bypass class of bug and CVE-2010-4083.

Verdict

Postulate's manual mmap/stack memory has no auto-zero. Fits directly into the project's own multi-error/IDE-diagnostics goal: an uninitialized-read warning is exactly the kind of thing worth flagging, not silently compiling.

Real, dated -O2/-O3 miscompilation regressions

Not one incident but a recurring class: GCC miscompiled the Linux kernel's initramfs zlib decompression at -O3 in 2021 (Linus Torvalds flagged it directly); GCC Bugzilla #106187 and fresh 2025 LLVM issues (#128528, #122496) show this remains an open, ongoing risk even in decades-old, heavily-fuzzed toolchains.

Verdict

The actionable lesson isn't a single test case — it's a discipline: build a differential-testing corpus that runs every fixture at -O0 through -O3 and diffs the runtime result, automatically, on every change.

Sources: LKML thread · GCC Bugzilla #106187

Pointer↔uintptr_t↔pointer provenance loss

A pointer round-tripped through an integer type can, under LLVM's formal provenance model, lose the "permission" the optimizer associates with the original pointer — a subtle, rarely-tested miscompilation source in optimized code.

Verdict

This is an explicit Postulate feature (as-cast pointer↔uintptr↔pointer). Test the full round trip — cast to uintptr, do arithmetic, cast back, dereference — at -O0 vs. -O3.

Unsigned underflow is defined — and dangerous precisely because it is

size_t len = 0; len - 1 wraps to the type's maximum value, silently, with no UB and therefore no optimizer "help" catching it — a classic buffer-overrun trigger when it feeds a loop bound or index.

size_t len = 0;
for (size_t i = 0; i < len - 1; i++) buf[i] = 0;  // len-1 == SIZE_MAX
Verdict

Postulate's unsigned types will have the identical wraparound. Confirm it's consistent across every -O level and consider whether an unsigned-underflow diagnostic belongs in the IDE-diagnostics goal.

Mixed signed/unsigned comparison implicit conversion

C silently converts the signed side to unsigned in a mixed comparison, so -1 < 5u is false. Postulate's explicit-cast-only design likely rules this out entirely.

Verdict

Low priority — useful mainly as a negative test: confirm mixed-signedness comparison without an explicit cast is a compile error, not a silent conversion.

Multiple unsequenced side effects (i = i++ + i++)

Classic sequence-point UB. Postulate likely has no expression-level ++/-- (only statement-level), which may rule this out structurally.

Verdict

Worth one test of function-argument evaluation order determinism as the closest surviving analog.

goto fail; goto fail; — Apple's 2014 SSL bug

Not a compiler bug: a duplicated, unconditional goto silently skipped signature verification. Syntactically legal C, invisible to most static analysis.

Verdict

An argument for a specific IDE diagnostic: unreachable code after an unconditional jump, and duplicated consecutive statements.

Source: ImperialViolet

C++

mandatory

Two threads worth pulling on: template diagnostics as the thing Postulate's own roadmap names as the anti-pattern to avoid, and the multi-file/ABI mismatch history as a preview of what Edsger's own cross-file use resolution needs to close off from the start.

SFINAE: substitution failure isn't reported, it's just silent removal

When template substitution fails, the standard doesn't treat it as an error — the compiler just drops that overload. Once every candidate is gone, the final message describes the symptom ("no matching function") never the cause.

template<class T>
auto f(T t) -> decltype(t.foo());  // silently removed for any T without .foo()
Verdict

The direct argument for Postulate's generics to report constraint failures as first-class errors at definition-check time, not as silent candidate pruning discovered only at the call site.

Sources: SFINAE, Wikipedia

Errors report from inside the generic body, levels deep

Because templates type-check only after substitution, a bad call-site argument is reported from inside the definition, often several instantiation levels down, with one mistake triggering a cascade of unrelated-looking errors in everything that depended on it.

Verdict

This is precisely what Postulate's roadmap names by name as the anti-pattern to avoid, in favor of Rust's two-location model: check the generic's own body once against its declared contract, then give a monomorphization failure a single point of blame at the call site.

Concepts fixed when constraints are checked, not what templates express

C++20 concepts move the check earlier — before instantiation — so failures name a constraint instead of unwinding an instantiation trace. The fix was entirely about timing, not new type-system power.

Verdict

A real precedent for Rust's approach, but Postulate's v1.2 plan (unconstrained generics) means this applies as a signpost for later: unconstrained generics reintroduce a version of the "nothing to check against" problem this was built to solve.

Two-phase lookup's typename/template tax

Dependent names default to "value" until instantiation, forcing disambiguator keywords purely to help the parser — a self-inflicted ambiguity from deferred checking, not a real semantic issue.

Verdict

Worth avoiding by design if Postulate generics ever reference a type parameter's own members — resolve it structurally rather than with a user-facing disambiguator.

Even Rust's trait-bound errors aren't perfect

Rust has its own open issues with confusing supertrait-bound messages — but every one is still anchored to one named, textually-local requirement, never a multi-level instantiation trace.

Verdict

Calibration, not a new problem: good diagnostics require declared bounds to check against. "Add constrained generics" and "add good generic diagnostics" are the same milestone.

Monomorphization bloat is orthogonal to everything else about templates

Every distinct instantiation is a fully separate code copy — no structural sharing even between identical layouts — producing real compile-time and binary-size blowup, independent of SFINAE, specialization, or variadics.

Verdict

Applies to Postulate's planned monomorphization exactly as-is. Plan for instantiation deduplication (structurally-identical types share codegen) from day one, not as a later optimization.

Source: thePasture: compile times & binary sizes

Deep recursive instantiation crashes the compiler, not just the build

GCC has shipped internal compiler errors and segfaults, not clean diagnostics, on deeply recursive template metaprogramming exceeding its instantiation-depth limit.

Verdict

Edsger's monomorphizer needs an explicit, gracefully-diagnosed recursion cap tested before shipping — a typo shouldn't be able to crash the compiler.

Source: GCC PR 54318

Member-function operators break symmetry with implicit conversions

a + b as a member function desugars to a.operator+(b), so an implicit conversion works for the right-hand operand but not the left — a + 1 compiles, 1 + a doesn't, for an operator that should be symmetric.

Verdict

Postulate's free-function-only operator declarations (operator ==(a: A, b: B)) already sidestep this whole class — worth a test confirming both operand orders resolve consistently when only one direction is declared, since that's the remaining risk.

Source: Effective C++ item 24

One-direction-only comparison overloads are silently order-dependent

Defining operator==(A, int) without the mirror operator==(int, A) means a == 5 and 5 == a can silently take different code paths, with no compiler warning.

Verdict

A confirmed Postulate gap — operands need not match types today, with no enforced mirror overload. Decide and test: require the mirror, auto-derive it, or diagnose its absence.

Source: Daily bit(e) of C++

Spaceship doesn't imply equality

A user-provided (non-defaulted) operator<=> does not auto-generate operator== — a rule that surprises people expecting "one operator, everything follows."

Verdict

Only relevant if Postulate ever unifies ordering under one operator — a cautionary tale that equality and ordering are distinct enough to need separate, independently correct implementations.

Ambiguous overload resolution via multiple implicit conversions

Two overloads each reachable via a different implicit user-defined conversion, neither strictly better, rejects the call — and adding an unrelated overload elsewhere can retroactively break it.

Verdict

Substantially defused already by Postulate having no implicit coercion; worth one test that exact-type overload resolution gives a clean "no match" rather than a near-match guess.

The One Definition Rule: silent, undiagnosed miscompilation across files

Two translation units defining the same symbol differently is UB with no diagnostic required — the linker may pick either, or under LTO, blend them. Real instances: Firefox with GCC8+LTO, MySQL blocked from LTO builds until patched.

Verdict

Edsger's namespace/use imports create the same surface. Make a signature mismatch across files a hard compile-time error, resolved against one canonical declaration — something C++'s linker structurally never checked.

Sources: Firefox Bugzilla 1516758 · "Oops!... I violated ODR again"

Linkers match by name only, never by signature

A function declared one way in file A and defined incompatibly in file B links "successfully" — wrong argument count, type, or ABI produces silently wrong codegen at the call site, not a link error.

Verdict

Directly relevant to use-based imports: Edsger should type-check every imported symbol against its real definition itself, rather than delegating that guarantee to a linker that structurally can't provide it.

ABI-level layout drift: GCC5's dual std::string

A struct-layout change shipped behind a build-time macro; mixing object files built with different macro values produced link errors or silent runtime corruption from treating one layout as the other.

Verdict

If Postulate's struct/ABI layout ever changes between Edsger versions, mixing object files from different versions should be a refused link, not a silent mismatch — cheap to add a layout fingerprint now.

Source: GCC libstdc++ dual ABI manual

Wrong nsw/nuw flags let a middle-end pass poison correct IR

nsw/nuw are a frontend's promise to the optimizer ("this never overflows"); real LLVM bugs have come from passes incorrectly attaching or propagating them, making transformed IR more poisonous than the source ever was.

Verdict

Directly actionable: Edsger's codegen should not emit these flags unless it has actually proven the precondition — not "the arithmetic looks like it probably doesn't overflow."

Sources: llvm/llvm-project#114903 · Lee et al., PLDI'17

Wrong noalias/alias-analysis metadata reorders memory operations

Multiple real LLVM bugs (TBAA/GVN replacing a pointer with undef, BasicAA returning NoAlias for pointers that could actually alias) show that bad alias metadata — from a compiler bug or an over-confident frontend — silently drops or reorders stores.

Verdict

Forward-looking to own *T: if ownership info is ever lowered to noalias hints, get the proof obligation right first. A wrong hint here is worse than no optimization at all.

Sources: llvm/llvm-project#122537 · #98978

LTO opens cross-unit miscompilation classes that don't exist without it

Whole-program visibility both fixes and creates bugs — documented cases include LTO replacing main's body with an infinite loop, and academic fuzzing finding non-trivial miscompilation rates specifically under LTO.

Verdict

Lower priority until Edsger does cross-module/whole-program optimization across use-imported namespaces — revisit then.

Source: Randomized Stress-Testing of LTO (ISSTA'15)

Strict-aliasing violations regress silently across optimizer versions

Type-punned code often "works" under weak optimization and breaks only once a later compiler version's stronger alias analysis notices — the same source, recompiled, produces a silent behavior change with no error at either point.

Verdict

Relevant to Postulate's manual-mmap model: decide what aliasing assumptions, if any, opt may make about two differently-typed pointers into the same raw memory region.

Transient out-of-bounds pointer arithmetic is UB even when it "comes back in bounds"

&x - 1 + 1 is UB despite looking harmless and running fine today — the same "assume UB never happens, delete the check" reasoning as signed-overflow UB, applied to pointers instead of integers.

Verdict

Given Postulate's real pointer arithmetic, this needs an explicit, documented answer: are transient out-of-bounds intermediate pointers permitted? opt must not assume in-boundedness beyond what the semantics actually guarantee.

Source: research!rsc: C and C++ Prioritize Performance over Correctness

Go

mandatory

Go is the useful control group: no pointer arithmetic, no operator overloading, defined (not UB) overflow — and yet its own bug tracker, and its own runtime built on the exact futex/mmap primitives Postulate exposes raw, still surface real, hard-won lessons.

The loop-variable-by-reference bug (fixed in 1.22, after 12+ years)

Go's for loop reused one variable binding across every iteration; a closure or goroutine capturing it saw whatever value it held when it ran, almost always the last one.

for i := 0; i < 3; i++ {
    go func() { fmt.Println(i) }() // pre-1.22: prints "3 3 3"
}
Verdict

Postulate has no closures, but a ref parameter or a function-type variable capturing a loop-scoped local by address reproduces the exact bug if storage is reused across iterations. Test: take a pointer inside a loop, store each into an array, dereference all after the loop — each must see its own iteration's value.

Source: go.dev/blog/loopvar-preview

Silent narrowing conversion → a real Kubernetes CVE

Trail of Bits found int32(port) silently truncating an out-of-range int with zero runtime check — kubectl expose --port=4294967376 wrapped into a small, valid-looking port number.

port, _ := strconv.Atoi(userInput)
p := int32(port)  // silently wraps, no panic
Verdict

Postulate's explicit-only as-casts are already stricter than Go's implicit narrowing — but the wraparound itself is the same shape. Test large-value narrowing casts across every width pair and confirm the wrap semantics are defined and documented.

Source: gosec G115 writeup

Defined signed overflow, and Go's own open INT_MIN / -1 question

Go deliberately specifies wraparound over UB — then spent four separate proposal threads (#19624, #30209, #30613) debating checked-arithmetic types anyway. A still-open spec issue (#1764) asks Go to define int8(-128) / -1 explicitly.

Verdict

LLVM's sdiv/srem on this exact input is UB unless explicitly guarded. Since Postulate promises defined semantics, this needs a guard in codegen at every signed width — not an inherited LLVM default.

Source: golang/go#1764

Truncating %, not floored modulo

Go's own designers explicitly chose truncation (-16 % 7 == -2) over Python-style flooring, to keep "remainder" strictly separate from "mathematical modulus."

Verdict

Pin down and document Postulate's own convention for negative operands across every signed width — cheap to verify, easy to get silently wrong porting an idiom from another language.

Source: golang/go#448

Float-to-int overflow sign-flips, with no defined behavior

int32(float32(2^31)) gives -2147483648 — a spec gap Go has left open for years (#19405).

Verdict

Postulate's float→int as-casts need an explicit, tested out-of-range answer — saturate, wrap, or trap — rather than inheriting whatever fptosi happens to do.

NaN permanently strands map keys

NaN != NaN means a NaN map key can never be retrieved or deleted again — plus a distinct historical Go compiler bug (#2609) from comparing floats via memcmp instead of real float equality.

Verdict

Forward-looking to any future hash container. More immediate: confirm no Edsger-generated equality lowering for float-containing structs ever falls back to bitwise memcmp.

Sources: golang/go#20660 · #2609

nil map panics on write, nil slice doesn't

Two "empty by default" types with opposite contracts — every reference-ish type in Go (map, slice, chan, func, pointer, interface) has its own subtly different nil rule.

Verdict

Not applicable to Postulate's current pointer/array model — but a clean design lesson for whenever a hash-map type gets added: pick one nil contract, apply it uniformly.

A typed-nil pointer boxed into an interface isn't nil

Go's most infamous gotcha: err != nil can be true even when the concrete pointer inside it is nil, because the interface value still carries type info.

Verdict

Not applicable today (no interfaces/boxing) — flag as a future risk only if Postulate ever adds tagged unions or a boxed "any" for the verification system.

Arrays are value types — a lesson Postulate can do better than Go at

Assigning or passing a Go array copies every element, correctly per spec, but constantly surprises people used to slice-style reference semantics living right next to it syntactically.

a := [3]int{1, 2, 3}
b := a       // full copy
b[0] = 99
fmt.Println(a[0]) // still 1
Verdict

Postulate's fixed arrays are presumably value types too. Since Postulate has real ref parameters (Go has none), this is a place to be more explicit than Go: test that array-in-struct copy, by-value array parameters, and ref-parameter array aliasing are all airtight and unambiguous.

Value-receiver methods silently mutate a copy

A method with a value receiver operates on a copy; mutations vanish on return, with no diagnostic distinguishing it from a pointer receiver at the call site.

Verdict

Largely defused by Postulate having no implicit receivers at all — still worth a positive regression test that ref/pointer parameters reliably mutate and by-value parameters reliably don't, including through an overloaded operator taking self by value.

append() aliases or reallocates based on hidden capacity

The exact same call site either mutates the shared backing array or silently breaks aliasing, depending on runtime capacity invisible in the type.

Verdict

Not applicable today (fixed arrays only) — essential input for whenever a growable-array type is designed: make the aliasing/reallocation boundary statically visible, or route it through the planned own-pointer model where ownership is unambiguous by construction.

A real, shipped optimizer-pass miscompilation: the "prove" pass

Go's SSA backend "prove" pass (which eliminates bounds checks via inferred value ranges) has shipped real, incorrect range assumptions — a check silently removed because the analysis was unsound, not because the check was actually redundant.

Verdict

The exact failure mode most relevant to Edsger's own optimizing middle end. Recommend differential-testing every fixture at every -O level, with particular attention to anything relying on a bounds check or the pointer-arithmetic direction rule (p+n valid, n+p rejected).

Source: Jakub Ciolek: When the compiler lies

Escape-analysis heuristics drift silently across compiler versions

A struct that stack-allocated in Go 1.23 started heap-allocating in 1.24, undocumented in release notes — an internal optimizer heuristic changing observable behavior across a version bump.

Verdict

Postulate's manual, GC-free memory model has no equivalent "escape analysis" to drift — a genuine structural advantage. Discipline lesson: pin exact expected codegen per -O level in golden tests so any future Edsger lowering-strategy change is caught by regression, not discovered in production.

Source: golang/go#73536

Go's own runtime has shipped real futex lost-wakeup bugs

Multiple filed Go runtime issues (#55120, #24608, #22398, #62451) show goroutines permanently blocked in futex() — the classic "wakeup arrives between the condition check and the wait call" race, in a hand-rolled scheduler built directly on raw futex.

Verdict

Directly shapes the design of Postulate's future std::mutex/condvar (already roadmapped on sys_clone/sys_futex): the waiter must re-check its condition atomically with respect to the waker, handle spurious wakeups, and account for wake-count-vs-waiter-count races — the exact bug classes Go's own scheduler hit in production.

Sources: golang/go#55120 · #22398

mmap/madvise semantics drift across kernels and flags

Go's allocator hit real memory corruption from mmap/madvise interaction with newer kernel features (#35777), and had to choose carefully between MADV_DONTNEED (safe, always faults) and MADV_FREE (faster, but "maybe still there" until reclaimed).

Verdict

This is Postulate's exact manual sys_mmap/sys_mremap/sys_munmap surface, with no GC to smooth over a mistake. Test mremap growth/shrink at real page boundaries and double-munmap/use-after-munmap behavior explicitly — should trap, never silently corrupt.

Source: golang/go#35777

Go's generics retrospective: the operator-overloading gap they didn't have to have

A decade of public debate, then a design critics call readability-hostile — and because Go has no operator overloading, generic numeric code needs awkward constraints.Ordered-style interfaces just to use +/< generically at all.

Verdict

Primary design input for v1.2: Postulate already has real operator overloading, so generic code should be able to use a type parameter's overloaded operators directly, instead of reinventing Go's constraint-interface plumbing after the fact.

Source: Go Type Parameters Proposal

defer is function-scoped, not block-scoped

defer f.Close() inside a loop holds every resource open until the whole function returns, not each iteration — routinely exhausts file-descriptor limits.

Verdict

Not applicable (no defer) — but the underlying lesson generalizes directly to whenever Postulate designs scope-exit cleanup for own *T: tie release to the actual lexical scope the resource was acquired in, not the nearest enclosing function.

Rust

mandatory

The most heavily-weighted track, on purpose: Postulate's planned own *T/ghost-map memory-safety model is a direct alternative to Rust's borrow checker, and needs an explicit answer for the two, quite different, historically-real failure classes Rust has actually hit.

Self-referential structs force unsafe/Pin — and Postulate simply doesn't try

The borrow checker can't express "field B references field A of the same struct," because moving the struct invalidates B with no way for the type system to update it. Rust's fix, Pin, is subtle and still forces unsafe to construct the reference at all.

Verdict

Postulate's ghost-map tracks address liveness, not intra-struct aliasing — a struct holding a raw *T into a sibling field is simply outside what the check covers. Worth stating explicitly in design docs: this is an avoided problem, not a solved one.

Sources: RFC 3467 · Cloudflare: Pin and Unpin

The "get-or-insert" false positive — flow-insensitivity rejects safe code

NLL reasons about lifetimes as regions, not per-branch control flow, so returning a mutable reference from one match arm and computing a fresh one in another is rejected even though the two borrows never coexist at runtime — the canonical "the borrow checker is technically wrong" example.

Verdict

Postulate's ref parameters have no aliasing enforcement at all today, so this specific false-positive can't happen — but the corresponding true positive (two live mutable aliases to the same data) is also currently undetected. If exclusivity checking is ever added, it faces the identical region-vs-flow-sensitivity choice Rust already got wrong once (motivating the still-in-progress Polonius rewrite).

Sources: Polonius alpha on nightly · Limitations of the Rust Borrow Checker

Disjoint-field borrows: whole-struct conservatism

The checker analyzes one function at a time, so a method call that only touches one field is treated as if it might touch the whole struct — blocking a simultaneous, genuinely-safe borrow of a different field.

Verdict

Doesn't exist in Postulate today (no field-granularity aliasing model at all) — not solved, just not yet attempted. Would resurface exactly this way if per-field ownership is ever added.

Source: babysteps: the borrow checker within

"Fighting the borrow checker" is Rust's own measured #1 adoption barrier

Rust's 2023 survey: 31% of non-users cite perceived difficulty as their primary reason to avoid the language; 24% of people who tried and quit cite difficulty specifically.

Verdict

The strongest point in Postulate's favor in this whole survey: no lifetime syntax, no elision rules, no fighting-the-checker mental model to teach, since verification is automatic and compiler-inserted rather than programmer-reasoned. The likely tradeoff — a different learnability cliff around "this path doesn't consume/free the own *T" errors — is untested and worth watching for once real programs use it.

Source: 2024 State of Rust Survey

noalias is weaker than what Rust actually needs to claim

Rust wants "this &mut T aliases nothing, for its whole lifetime, even across nested calls" — but LLVM's noalias attribute technically only means "nothing in this function's own scope." The mismatch has caused both missed optimizations and real miscompilations.

Verdict

The single most actionable finding in the whole survey for Edsger's opt integration: own *T's linear, exclusive semantics is a stronger claim than plain LLVM noalias. Naively attaching the attribute without matching Rust's still-evolving rules is a realistic path to silent miscompilation at -O2/-O3.

Sources: rust-lang/rust#53105 · PR #106371

A real, shipped noalias miscompilation from inlining + loop unrolling

Enabling "mutable noalias" in 2021 broke the ring crypto crate: LLVM failed to give duplicated, inlined-then-unrolled copies of a function distinct alias-scope tags, so it concluded pointers from different copies could never alias — even though at runtime they did. GCC miscompiled the equivalent pattern too.

Verdict

Not Rust-specific — an LLVM-pipeline hazard Edsger shares exactly, since it routes through the same inlining/unrolling/GVN passes. If ownership-derived scope metadata is ever emitted, it must be tagged per dynamic-object-identity, not per static call site.

Source: rust-lang/rust#84958

Forming a reference is itself a claim — even in unsafe code

Building an intrusive linked list in unsafe Rust: merely creating a &mut to a node, without writing through it, was treated by Stacked Borrows as invalidating other live pointers to the same memory — even same-node self-loops in a one-element list. The fix abandoned references for raw-pointer reads/writes entirely.

Verdict

Directly relevant to Postulate's own raw-pointer arena/buffer patterns. Because Postulate has no reference type distinct from a plain pointer, it structurally avoids "forming a reference is an event" — a real advantage, as long as Edsger never attaches Rust-style reference-derived LLVM attributes to a plain *T or own *T.

Source: Chad Austin: Unsafe Rust Is Harder Than C

The actix-web soundness controversy

A 2020 audit found a widely-deployed framework (100+ unsafe blocks) handing out multiple live mutable references to the same data, plus unsound reference-mutability coercion and lifetime extension — a real, production, use-after-free-shaped bug from an expert author.

Verdict

Postulate has no safe/unsafe split at all — every line is "unsafe-shaped" by Rust's own standard. The strongest possible argument for prioritizing the own/ghost-map work: in Rust this class of bug is at least contained to flagged unsafe blocks; in Edsger today it can appear anywhere, with no tooling to flag it as suspicious at all.

Sources: The Register · Raph Levien: The Soundness Pledge

264 unsafe-Rust soundness bugs, found by one automated study

RUDRA found 264 previously-unknown memory-safety bugs across published crates via automated pattern analysis — 76 CVEs, 112 RustSec advisories — from uninitialized-memory misuse, bounds violations, and aliasing violations.

Verdict

Every one of these categories maps onto Postulate's raw-syscall/manual-mmap surface today with zero automated detection — the empirical case that this bug class is common, not theoretical, even in a language whose whole pitch is memory safety.

Source: RUDRA (Bae et al.)

Integer overflow's dual-mode design is still debated a decade later

RFC 560: panic in debug builds, silently wrap in release. A deliberate defense-in-depth compromise, and still contested (RFC PR #2635 proposed always-panic-in-release for usize) — a documented "worked in testing, broke in prod" trap when a bug only panics under debug_assertions.

Verdict

Open question this research could not resolve from available information: what does Edsger's own overflow behavior do today, and does it change across -O levels? Given Postulate shares the exact opt -O0..-O3 pipeline, the identical debug/release-parity trap applies — resolve and document this explicitly per integer width and per -O level now.

Sources: RFC 0560 · Myths and Legends about Integer Overflow in Rust

get_unchecked: unchecked-access UB from composing two reasonable unsafe trait impls

Pre-1.52, Zip's internal optimization called an unsafe trait method twice for the same index under certain conditions — UB that emerged from composition, not from any single function looking wrong in isolation.

Verdict

Worth checking whether Edsger's own array indexing ever elides bounds checks at higher -O levels the way Rust's get_unchecked intentionally does — and whether that's -O-level-dependent (same debug/release-parity risk as overflow, above).

noalias in return position: a distinct, separately-discovered bug

Return-position pointers were mistakenly marked noalias, implying the returned pointer aliases nothing reachable before the call — false for an identity-like function. A second, independent discovery from the same underlying attribute-emission mechanism as the parameter case.

Verdict

If Edsger ever emits noalias/dereferenceable on functions returning own *T, test the pass-through/identity case specifically — a second, independent failure mode from the parameter-position bug above.

Source: rust-lang/rust PR #106371

Lifetime elision isn't a scope, it's a placeholder — and Postulate simply has none

'a looks like a concrete region of code but is a parametric placeholder resolved per call site; &mut T is invariant in T while &T is covariant, and lifetime subtyping runs "backwards" from intuition.

Verdict

The strongest "we don't have this problem, by construction" item for the v1.2 generics design: monomorphized, lifetime-free type parameters have no elision-rule table and no variance question at all, because there's nothing for a lifetime to be co/contra/invariant with. Worth stating as a deliberate, permanent scope exclusion in the design notes.

Miri: a dynamic oracle for what the type system can't statically prove

Because the type system can't check unsafe code's invariants, Rust built a separate interpreter that dynamically enforces its aliasing model at runtime — catching violations only in whatever tests it's actually run against.

Verdict

Useful contrast for evaluating Why3: Postulate is aiming for static, sound verification — strictly stronger than Miri's test-coverage-dependent checking if achievable, but historically far harder to scale. Worth an explicit plan for verification timeouts/non-termination on larger own *T-heavy programs before that becomes a surprise.

Laundering a shared reference into a mutable one via transmute

Explicitly documented as UB: transmute::<&T, &mut T> violates the exclusivity the optimizer assumes for &mut, independent of whether the underlying memory is "really" exclusively accessed at runtime.

Verdict

The direct Postulate analogue: casting away a *const T qualifier via as and writing through it. Recommend as the first concrete test once *const T enforcement is complete — does opt ever get told a pointer points to immutable data in a way that lets -O2/-O3 cache a read across a cast-away write?

Source: internals.rust-lang.org

C# · Java · Python · JavaScript · PHP

surveyed

Aggressively filtered: no GC, no exceptions, no dynamic typing, no reflection, no closures, no OOP inheritance in Postulate, so most of what these five languages are famous for simply doesn't transfer. What's left is genuinely portable — numeric representation, value-type copy semantics, text encoding, and operator-consistency rules.

0.1 + 0.2 ≠ 0.3, everywhere, by construction

Every IEEE-754 language hits this identically — decimal fractions have no exact binary representation. Pure consequence of base-2 mantissas, not a runtime quirk of any one language.

Verdict

Postulate's float32/64 inherit this exactly. Low actionable risk — worth one "this is not a bug" regression test, and a documented epsilon-comparison idiom before someone files it as one.

Source: 0.30000000000000004.com

Every mainstream language guarantees NaN != NaN — Postulate doesn't

IEEE-754 mandates NaN compares unordered everywhere from C to Python to JavaScript. Postulate's ordered-fcmp lowering makes both == and != read false for NaN — not an obscure IEEE detail, a deviation from the one NaN property every other language relies on.

Verdict

Highest-priority float finding in this survey. Anyone porting intuition (or code) from any other language will get this backwards. Needs a prominent test case and a documented rationale — or reconsidering unordered predicates for != specifically.

Sources: IEEE 754 predicates · Rust's Eq trait (excludes floats for exactly this reason)

Truncating vs. flooring division/modulo — a real, named split

C, Java, JS, C#, Go, and hardware division all truncate toward zero; Python floors toward −∞. Java 8 added Math.floorMod/floorDiv alongside %// specifically because truncation surprised developers doing cyclic-index arithmetic.

Verdict

Pick and document one convention (truncating matches LLVM's native sdiv/srem and C's hardware reality) and test the boundary cases explicitly: negative dividend, negative divisor, and the INT_MIN edge case above.

Sources: evanjones.ca · Java Math.floorMod rationale

Fixed-width overflow: a five-language taxonomy, and Rust's model is the closest fit

The spectrum: C — UB, exploitable by the optimizer; Java/C# — always silent wraparound; Swift — traps by default, with explicit &+/&-/&* for intended wrapping; Rust — panics in debug, wraps in release, plus a discoverable checked_*/wrapping_*/saturating_*/overflowing_* family for explicit intent.

Verdict

Since Postulate has no exceptions/panics as an escape hatch, "trap" is weaker here than in Swift/Rust. The Rust named-function-family pattern is the best-fit portable lesson: pick one default (wrap, matching native hardware add/sub/mul) and offer explicit named alternatives instead of silent, undocumented behavior.

Sources: Swift overflow operators · regehr.org: How Integers Should Work

Float→int cast truncates toward zero; rounding is always a separate, named operation

C, Java, and Python's narrowing float→int casts all truncate toward zero, not floor and not round. Round-to-nearest is always explicit (Math.round, Python's round()), and several use round-half-to-even rather than the grade-school half-up rule.

Verdict

Confirm Postulate's float→int as cast truncates toward zero (matching LLVM's fptosi/fptoui). Flag as a near-term gap: users will want an explicit round-to-nearest distinct from the truncating cast, with a deliberately chosen tie-break rule.

Source: CMU: Danger in Floating-Point-to-Integer Conversion

UTF-16 surrogate pairs, and the UTF-8 analog Postulate should actually worry about

JS/Java/C# count UTF-16 code units, not codepoints — "😀".length === 2 in JavaScript — and naive slicing can split a surrogate pair, a real, documented input-sanitization-bypass bug class.

"😀".length  // 2 in JavaScript: one astral character, two UTF-16 code units
Verdict

Postulate's rune[N] (UTF-8 codepoints) has no surrogate pairs — but char[N] (raw bytes) is exactly the structural equivalent of a "code unit," and slicing it at an arbitrary byte offset can just as easily split a 2–4-byte UTF-8 sequence mid-character. Test slicing/indexing char[N] at a non-boundary offset, and decoding a truncated multi-byte sequence into rune[N] — does it error, produce a replacement character, or read out of bounds?

Sources: Mathias Bynens: JS Unicode problem · usd HeroLab: overlong UTF-8 encodings

C#'s ==/!=/GetHashCode consistency contract has no compiler enforcement

C# lets operator== be overloaded independent of !=, Equals, and GetHashCode — the compiler only warns (CS0660/CS0661). The most common real bug: define == for value semantics, forget GetHashCode, and every Dictionary/HashSet silently treats equal values as different keys.

Verdict

Postulate's documented gap exactly: == can be defined without !=, with zero enforced consistency. Consider a Rust-style split (a marker trait/convention gating which types can be hash keys) or simply require the pair to be defined together — cheap, and closes the single most common instance of this bug class.

Sources: C# CS0661 · Equals/GetHashCode pitfalls

Struct-in-collection and mutate-through-a-copy footguns

C#'s classic value-type traps: mutating a struct reached through a property getter silently mutates a temporary copy and the write vanishes; foreach over structs had to be special-cased to forbid mutating the iteration variable, because it's a copy.

Verdict

Postulate structs are value types too, copied on pass/return with no reference-type escape hatch except explicit pointers. Test that mutating a struct field reached through a function call that returns a struct by value is provably impossible (never silently "looks like" it worked) — and that struct-in-struct field chains hold the same guarantee. Postulate's requirement for explicit ref to get by-reference semantics should already make this lower-risk than C# by design; the test is confirming that explicitness actually holds everywhere.

Source: Steven Giesel: mutable value types are evil

PHP/JS coercion as a design cautionary tale — culturally real, weakly documented

"PHP: A Fractal of Bad Design" is widely credited with helping shift language-design culture toward explicit typing, but no primary Rust/Go/Swift design doc directly cites it as a stated rationale — the influence is cultural, not a documented engineering citation.

Verdict

Directionally confirms what's already obvious: Postulate's literal-anchoring-instead-of-coercion design avoids this bug class entirely. Not worth a dedicated test beyond what "no implicit coercion" already covers — a design-philosophy confirmation, not an action item.

Source: eev.ee: PHP, a fractal of bad design
